# 出图规则（argmap）

把一篇文章的**主张与论证结构**抽成节点图，用 `render_argmap` 渲染成一张手绘风格的配图。内容规范借自 NodeGraph（MIT），按我们的用途改写。

**检验标准只有一条：看这张图比读那篇文章更快吗？** 更慢的图，无论多完整，都算失败。两个症状：标题在命名话题而不是给出断言；节点长到读者放弃。

## 工作顺序（必须按这个次序）

1. **读完全文。**
2. **先选版式**（第二节）。不要先抽节点再找版式：先抽出来的节点会被画成一条因果链，选版式就成了走过场。
3. **按选定的版式抽节点**（第一节，加第三节该版式的额外字段）。
4. **写 JSON，调用 `render_argmap`**；有警告就改了重出。

## 一、抽论证

### Kernel test：什么才配进主干

kernel = 原作者（或这篇文章）做了、别人没做的事。找 4–8 个，再问：**整篇能不能从这组重建？** 不能，就还漏一个；丢掉某个仍能重建，它就不是 kernel。

- **CORE** → 主干节点（`row: 0`）。信号：作者自己命名的现象或指标；他引入的定义；分析性反转；在两种可能之间下的判断；挂在数字上的解读。
- **SUPPORTING** → 子节点（`row: 1`），挂在它支撑的那个主干下。
- **非 kernel**（过渡、复述、套话、厂商自我介绍）→ 不给节点。

主干节点之间的关系按版式来：`flow` 和 `fishbone` 要说清「从哪个来、使能哪个」；`timeline` 的主干按日期排，每个事件带 `date`；`tree`、`compare`、`debate` 的主干之间本来就是并列或对照，不要硬加推出关系。

### 八条写作原则

1. **先固定一个具体读者**（写进 `reader`）。术语没解释就不许出现。
2. **标题必须是可证伪的断言**。「概述」「架构」「背景」零信息。
3. **一个 landmark**：一句话说出问题与答案，放在图顶。每个节点都要能回答「它怎么服务这句话」。
4. **一点一节点，结论先行**：一句话说完。
5. **旧词接新意**：子节点第一句用父节点用过的词开头。
6. **一名一物**：同一个东西全图只有一个名字。
7. **背景按需给**：定义放在需要它的那个节点里。
8. **最后再砍一遍**（必做）：砍铺垫、砍形容词、砍换个节点也成立的内容。

### landmark 要说人话

`landmark` 是图里最大的那行字，读者先看它。它必须同时交代两件事：**这件事属于什么领域**、**它到底在说什么**。写内部黑话等于没写。

- 反例：`三次按键的数据路：字节进、333 个 token 的世界、行改写出来`
- 正例：`AI 把终端做成了一个模型：背后没有 shell、没有文件系统，屏幕上的一切由它按次预测`

判断方法：把这行字单独发给一个不做这行的人，他能不能说出「这在讲哪一类东西」。说不出就重写。

### 溯源

- 每条来自原文的主张挂自己的出处：`quote` 放原文引文（英文照抄），`source` 放 URL。
- **零幻觉**：不许编数字、比较、引用。
- **我们自己的判断一律标 `kind: "our-take"`**，渲染成琥珀色，和来源主张分开。
- 溯源注（「裁判是 AI」「这条只有二手转述」「0.40 / 0.10 是作者举的假设例子」）放 `footnote`，不占节点。

## 二、选版式：先认体裁，再判结构

版式跟着论证结构走，体裁是判结构最快的线索。硬套版式会凭空加因果。

**第一步：认体裁，查下表得到候选版式。** **第二步：用结构核对**：原文里这几点之间，有没有作者写明的推出、反驳、先后关系？体裁给的候选和原文结构对不上时，以结构为准。

| `layout`               | 适合的体裁                                                           | 论证结构                                           | 不适合                              |
| ---------------------- | -------------------------------------------------------------------- | -------------------------------------------------- | ----------------------------------- |
| `flow` 推进链          | 事件调查、安全报告、单线论证的工程博客（「我们发现 X，所以改成 Y」） | 一步推一步，每步由上一步引出                       | 几个并列要点（会凭空加先后）        |
| `fishbone` 鱼骨        | 论文加第三方评审、反驳、复现实验的综述；「一个说法，三方检验」       | 一个主张被几条独立的线检验，汇成一个结论           | 只有一个来源的文章                  |
| `annotated` 正文加批注 | 带批注的内部文档、评审意见、HN / issue 讨论串、访谈里主持人追问      | 一份正文，多人在不同位置补充、反对、拍板           | 批注只有一两条                      |
| `tree` 目标树          | 路线图、方法论、框架介绍、「做好 X 的 N 个方向」                     | 一个目标拆成几个并列方向，方向之间没有先后         | 方向之间有依赖（改用 `flow`）       |
| `steps` 操作步骤       | How-to、Skill 实践、可复现工作流、安装配置教程                       | 有序步骤，每步有动作和产出，可能有「卡住时怎么办」 | 原则清单（改用 `tree`）             |
| `system` 架构拆解      | 工具 / repo 拆解、harness 设计、产品形态分析                         | 一个系统由几个部件组成，部件之间传数据或调用       | 只讲一个部件的好处                  |
| `compare` 对比         | 产品评测、新旧做法对比、成本对比、「A 还是 B」                       | 两三个对象在同一组维度上逐项比较，最后给结论       | 只有一个维度的对比                  |
| `timeline` 时间线      | 事故复盘、版本演进、一件事的来龙去脉、行业史                         | 事件按时间排列，时间本身就是论证的一部分           | 有日期但论证不靠时间（改用 `flow`） |
| `loop` 循环            | agent loop、反馈回路、飞轮、迭代流程                                 | 几步首尾相接、反复执行，有退出条件                 | 只执行一次的流程                    |
| `debate` 对辩          | 争议话题、正反方交锋、作者回应批评                                   | 两方针锋相对，一来一回                             | 单作者自问自答（改用 `flow`）       |

### 容易判错的七种情况

1. **工具 / repo 稿看正文在做什么，不看体裁标签。** 讲怎么装、怎么用 → `steps`；讲内部几个部件怎么连、数据怎么一步步被加工 → `system`；讲它比旧做法好在哪（正文里有「以前……现在……」「比 X 快 / 便宜」，而且至少两个维度）→ `compare`。`system` 的门槛：正文写出至少三个有名字的部件，并写明它们之间怎么交互。
2. **先解释一个反复执行的机制、再给配置建议的文章，用 `loop`。** 建议如果讲的是这个循环怎么停、怎么设上限，就挂成退出条件或子节点。
3. **`flow` 要求每一步都是作者写明的「由上一步推出」。** 「A 比 B 好，所以换成 B」是对比；一串并列的好处排成一行也不是推进链；「痛点 → 这个工具 → 效果」是产品介绍的套路，按正文主体选版式。
4. **`fishbone`、`tree`、`flow` 先问：读者要带走的是什么？**
   - 那个汇总出来的结论，几条线只是让人信服的理由 → `fishbone`。骨头要是互不依赖、来源或方法不同的几条线。
   - 每一项本身（清单、N 种模式、N 条原则）→ `tree`，即使文末有一句总结。
   - 事情怎么一步步查清楚的（调查报道）→ `flow`。媒体调查报道默认 `flow`。
5. **鱼骨的骨头必须是支持结论的论据。** 被逐条反驳的反对意见 → `debate`；讨论帖的原帖加高赞回复 → `annotated`。
6. **事故复盘按「X 年前」或日期组织的，用 `timeline`**，即使各事件之间也有因果。
7. **鱼骨的骨头要来自原文之外的检验，或原文明确并列的几个案例。** 「几条线」是你自己归纳的，先怀疑它是 `tree` 或 `flow`。

拿不准：有先后就用 `flow`，只有并列就用 `tree`。两者都不会凭空加因果。

### 版式轮换

同一条时间线上**不要连着三条用同一版式**。`compare` 最容易变成默认值。选版式前先调 `recent_layouts` 看最近几条用了什么；两个版式都能讲时，选最近三条没用过的那个。

## 三、Schema

```json
{
  "layout": "flow",
  "landmark": "一句话（问题 + 答案）",
  "reader": "一个具体读者",
  "footnote": "溯源注（可选，一行）",
  "article": { "title": "...", "url": "...", "published": "2026-10-13" },
  "nodes": [
    {
      "id": "K1",
      "kind": "thesis",
      "title": "可证伪的断言",
      "point": "一句话",
      "quote": "原文引文",
      "source": "URL",
      "col": 1,
      "row": 0
    }
  ],
  "edges": [{ "from": "K1", "to": "K2", "kind": "supports", "label": "可选" }]
}
```

- `kind`：thesis（主张）、evidence（证据）、rebuttal（反驳）、concession（让步）、result（实验）、our-take（我们的判断）、support（支撑）、decision（拍板）、question（疑问），以及下表各版式用的 step、check、pitfall、component、data、actor、event、turn、group。
- `edges` 的 `kind`：supports、refutes、qualifies、enables。
- `row: 0` 是主干，按 `col` 从小到大排；`row ≥ 1` 是子节点，挂在有边指向它的那个主干上。
- `fishbone`：第一个主干是鱼尾，最后一个是鱼头，中间的都是骨头。
- `annotated`：右栏批注是 `row: 1` 的节点，带 `author`。
- `point` 里的 `**加粗**` 会被去掉。
- 除了 `our-take` 和分组框，每个节点都要有 `source`；thesis、evidence、rebuttal、concession、result 还要有 `quote`。`render_argmap` 会先检查，缺了直接告诉你缺什么。

各版式的额外字段：

| `layout`   | 字段                                                                                                                                                              |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `steps`    | 主干是步骤（`kind: "step"`），按 `col` 编号；子节点用 `check`（验收）、`pitfall`（卡住时）或 `support`（命令）                                                    |
| `timeline` | 主干是事件（`kind: "event"`，转折用 `turn`），每个事件加 `date`                                                                                                   |
| `loop`     | 主干按 `col` 排成一圈；目的节点加 `"center": true`；退出条件是 `row: 1` 的子节点                                                                                  |
| `debate`   | 顶层加 `"sides": {"A": "作者", "B": "批评者"}`；交锋节点带 `side` 和 `col`（回合）；无 `side` 的 `row: 0` 节点是议题，无 `side` 的 `row: 1` 节点是我们的判断      |
| `compare`  | 顶层加 `"sides": ["对象 A", "对象 B"]` 和 `"dims": ["维度 1", ...]`；每个格子是一个带 `side`、`dim` 的节点；没有 `side` 的节点是底部结论                          |
| `system`   | 分组框是 `kind: "group"` 的节点；部件（`component` / `data` / `actor`）用 `group` 字段指明属于哪个框（可嵌套）；同一层里按 `row` / `col` 排网格；`edges` 画数据流 |

## 四、密度

- **全图 ≤ 10 个节点**；每个主干一般 ≤ 1 个子节点（`flow` 和 `annotated` 允许 2–3 个）。
- 每张卡：标题一行，正文一句话。
- 高宽比超过 1.8 时，时间线会把图裁成一小截：先砍节点或换版式，**不要缩字号**。

## 五、出图后自检

`render_argmap` 会报告卡片重叠、文字越出卡片、分组框标题越出框外、高宽比过高；有就改 JSON 重出。能看到图时，再看一眼：

- landmark 一句话说清问题与答案，外行能说出这在讲哪类东西
- 每个标题都能被证伪
- 版式是按结构判出来的，没有凭空加因果
- 每条来自原文的主张都有 `quote` 和 `source`
- 我们的判断是琥珀色，和来源主张分开
- 图比读文章快
